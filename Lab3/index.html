    Отчет по лабораторной работе №3. Упаковка FastAPI приложения в Docker, Работа с источниками данных и Очереди

    Цели

    Научиться упаковывать FastAPI приложение в Docker, интегрировать парсер данных с базой данных и вызывать парсер через API и очередь.

    Задание

    1. Упаковать FastAPI приложение, базу данных и парсер данных в Docker.
    2. Добавить вызов парсера из FastAPI по HTTP.
    3. Реализовать асинхронный вызов парсера через очередь с использованием Celery и Redis.

    Реализация

    В качестве основы использовалось FastAPI-приложение из ЛР1 и парсер из ЛР2

    Подзадача 1

    Для решения первой подзадачи были созданы отдельные контейнеры для базы данных, основного API и сервиса парсера. Основное приложение и парсер упакованы в разные Docker-образы на базе python:3.12-slim.

    В основном Dockerfile выполняются следующие действия: - задаётся рабочая директория /app - копируется файл requirements.txt - устанавливаются зависимости - копируется исходный код приложения - запускается uvicorn main:mainapp --host 0.0.0.0 --port 8111

    Отдельный Dockerfile для парсера устроен аналогично, но запускает сервис uvicorn main:app --host 0.0.0.0 --port 8112.

    Для управления всеми контейнерами используется docker-compose.yml. В нём описаны следующие сервисы: - db - контейнер PostgreSQL 16 - migrations - отдельный сервис для запуска alembic upgrade head - api - основное FastAPI приложение - parser - отдельный HTTP-сервис парсинга - redis - брокер сообщений и backend результатов Celery - celery_worker - воркер для фоновой обработки задач - celery_beat - сервис периодических задач

    В docker-compose.yml также настроены: - подключение общего файла .env через env_file в каждом сервисе, которому нужны настройки - depends_on для корректного порядка запуска контейнеров - healthcheck для сервисов db, api, parser и redis - том postgres_data для хранения данных PostgreSQL

    Основные значения конфигурации вынесены из docker-compose.yml в корневой файл .env. Для примера и воспроизводимости добавлен файл .env.template. В нём хранятся только те переменные, которые отличаются для Docker-окружения: - параметры PostgreSQL: POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB - строка подключения основного API к базе: APP_CONFIG__DB__URL - адрес сервиса парсера для основного API: APP_CONFIG__PARSER__BASE_URL - адреса Redis для Celery: APP_CONFIG__CELERY__BROKER_URL и APP_CONFIG__CELERY__RESULT_BACKEND - отдельная строка подключения парсера к базе: PARSER_DB_URL

    Переменные с дефолтными значениями, например таймаут парсера, имя очереди Celery и интервал периодического запуска, не дублируются в .env, так как они уже заданы в src/core/config.py.

    Таким образом, первая подзадача решает проблему развёртывания: всё приложение запускается одной командой docker compose up --build, а вся необходимая инфраструктура уже описана в одном файле конфигурации.

    Подзадача 2

    Во второй подзадаче был реализован вызов парсера из основного FastAPI приложения. Для этого в основном API добавлен маршрут POST /api/v1/parser/parse

    Принцип работы следующий: - клиент отправляет в основное API JSON с URL страницы книги - основное приложение принимает запрос и валидирует его через схему ParserRequest - далее сервис services/parser.py отправляет HTTP-запрос в контейнер parser - сервис парсера загружает страницу, извлекает название книги, описание и жанр - после этого данные сохраняются в таблицы genres и books - основной API возвращает клиенту результат работы парсера

    Отдельный сервис парсинга реализован как самостоятельное FastAPI-приложение. В нём: - создан маршрут POST /parse - используется пул соединений asyncpg для работы с PostgreSQL - строка подключения к базе читается из переменной окружения PARSER_DB_URL - загрузка HTML выполняется через requests - синхронный сетевой вызов оборачивается в asyncio.to_thread, чтобы не блокировать event loop

    Такой подход позволяет отделить парсер от основного API и сделать архитектуру более модульной. Основное приложение отвечает за приём клиентских запросов, а отдельный сервис парсера отвечает только за загрузку страницы и сохранение данных.

    Подзадача 3

    В третьей подзадаче был добавлен асинхронный запуск парсинга через очередь. Для этого в проект были подключены Celery и Redis.

    Redis используется в двух ролях: - как брокер сообщений для очереди задач - как backend для хранения статусов и результатов задач

    Конфигурация Celery вынесена в celery_app.py. В ней задаются: - адрес брокера broker_url - адрес backend результата result_backend - очередь по умолчанию parser - сериализация в формате JSON - отслеживание статуса выполнения задач - расписание для периодического запуска задач через celery_beat

    Для постановки задачи в очередь в основном API добавлен маршрут POST /api/v1/parser/parse-async. Он принимает URL, создаёт задачу Celery и сразу возвращает клиенту task_id, не дожидаясь завершения парсинга.

    Получение статуса задачи реализовано через маршрут GET /api/v1/parser/tasks/{task_id}. Клиент может по идентификатору узнать: - текущий статус задачи - готов ли результат - завершилась ли задача успешно - результат парсинга или текст ошибки

    Обработка фоновых задач реализована в tasks/parser_tasks.py: - задача parser.parse_url принимает URL - внутри задачи вызывается функция parse_url, которая отправляет HTTP-запрос в контейнер parser - после завершения результат возвращается в виде JSON и сохраняется в Celery backend

    Дополнительно реализованы периодические задачи: - celery_beat через заданный интервал ставит batch-задачу в очередь - batch-задача читает список URL из настройки settings.celery.periodic_parse_urls - затем для каждого URL создаётся отдельная задача парсинга

    По умолчанию периодический запуск выполняется каждые 300 секунд. Список URL также имеет значение по умолчанию в конфигурации приложения, но при необходимости его можно переопределить через переменную окружения APP_CONFIG__CELERY__PERIODIC_PARSE_URLS в .env.

    Итоговая конфигурация стала проще: в docker-compose.yml остались только сервисы, порты, зависимости, healthcheck и указание env_file, а сами значения окружения вынесены в отдельный файл.

    Основные маршруты

    В рамках лабораторной работы были реализованы следующие маршруты:

    Маршрут Назначение
    GET /health проверка работоспособности основного API
    GET /health на сервисе parser проверка работоспособности парсера
    POST /parse на сервисе parser прямой запуск парсинга страницы
    POST /api/v1/parser/parse запуск парсера через основное API
    POST /api/v1/parser/parse-async постановка задачи парсинга в очередь
    GET /api/v1/parser/tasks/{task_id} получение статуса задачи Celery

    Вывод

    В ходе лабораторной работы FastAPI-приложение, база данных, сервис парсинга и очередь задач были объединены в единую контейнеризированную систему. Было реализовано два способа вызова парсера: синхронный через HTTP и асинхронный через Celery и Redis.

    Использование Docker Compose упростило запуск всех компонентов, а разделение на отдельные сервисы сделало архитектуру более понятной и расширяемой. Очередь задач позволила вынести длительные операции в фон и добавить возможность периодического автоматического парсинга, что приближает проект к структуре реального production-приложения.
